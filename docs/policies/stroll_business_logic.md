# Stroll BUSINESS LOGIC

## Purpose

`Stroll` — bounded context мобільного застосунку для мотивації користувачів до щоденної фізичної активності через кроки, маршрути, квести, досягнення та статистику.

`Stroll` володіє:
- обліком фізичної активності користувача та кількості кроків;
- створенням і виконанням стандартних та налаштовуваних квестів;
- побудовою квестів на основі реальної відстані між двома географічними точками;
- відстеженням прогресу користувача у поточному квесті;
- системою винагород, рівнів та досягнень;
- збереженням історії виконаних квестів і статистики активності;
- локальним зберіганням даних для користувача без облікового запису та віддаленою синхронізацією для авторизованого користувача;
- формуванням даних для push-нагадувань про активність.

**NOT here:**
- фактичне отримання сирих даних від сенсорів смартфона — `Infrastructure`;
- отримання даних Google Fit — `Infrastructure`;
- робота з Google Maps API та розрахунок маршруту через зовнішній сервіс — `Infrastructure`;
- автентифікація та керування обліковими записами — `Infrastructure` / `Application`;
- фізична доставка push-повідомлень — `Infrastructure`;
- збір технічної аналітики Google Analytics / Firebase Analytics — `Infrastructure`;
- UI Android-застосунку та навігація між екранами — `Presentation`.

## Entities

| Entity | Basic Fields | Description | Invariants |
|---|---|---|---|
| `User` *(Aggregate Root)* | `uuid`, `displayName`, `level`, `totalSteps`, `totalDistance`, `createdAt` | Представляє локального або авторизованого користувача та його загальний прогрес. | `uuid` незмінний. `level >= 1`. `totalSteps >= 0`. `totalDistance >= 0`. Загальні лічильники не можуть зменшуватися внаслідок звичайного додавання активності. |
| `Quest` *(Aggregate Root)* | `uuid`, `title`, `description`, `type`, `status`, `targetDistance`, `targetSteps`, `startPoint`, `endPoint`, `routeDistance`, `progress`, `rewardRef` | Бізнес-завдання, яке має умови виконання та винагороду. Може бути стандартним або створеним користувачем. | `uuid` незмінний. Квест має додатний цільовий показник. Для маршрутного квесту задані початкова і кінцева точки та додатна відстань маршруту. Прогрес не може бути від'ємним або перевищувати 100%. Завершений квест не повертається у стан активного. |
| `QuestProgress` *(internal Entity — owned by `Quest`)* | `currentSteps`, `currentDistance`, `startedAt`, `completedAt` | Поточний стан виконання конкретного квесту. | `currentSteps >= 0`. `currentDistance >= 0`. `completedAt` встановлюється лише після досягнення цілі. Прогрес не може зменшуватися через коректне надходження нових даних активності. |
| `Achievement` *(Entity)* | `uuid`, `code`, `title`, `description`, `condition`, `reward`, `unlockedAt` | Нагорода за досягнення визначеної умови активності або виконання квесту. | `code` унікальний. Досягнення може бути отримане не більше одного разу для одного користувача. `unlockedAt` встановлюється один раз. |
| `ActivityRecord` *(Entity)* | `uuid`, `date`, `steps`, `distance`, `source` | Нормалізований запис фізичної активності, отриманий від пристрою або зовнішнього сервісу. | `uuid` незмінний. `steps >= 0`. `distance >= 0`. Джерело активності має бути визначене. Повторна синхронізація не повинна створювати дубль одного й того самого зовнішнього запису. |

## Quest Lifecycle

Новий квест створюється у статусі `AVAILABLE`, якщо він доступний користувачу, або `DRAFT` для налаштовуваного квесту до підтвердження параметрів.

Дозволені переходи:

| From | User-initiated | System-initiated |
|---|---|---|
| `DRAFT` | → `AVAILABLE`, `CANCELLED` | — |
| `AVAILABLE` | → `ACTIVE` | — |
| `ACTIVE` | → `CANCELLED` | → `COMPLETED` |
| `COMPLETED` | — (terminal) | — (terminal) |
| `CANCELLED` | — (terminal) | — (terminal) |

Правила:
- `DRAFT` може бути активований лише після успішної перевірки всіх параметрів.
- `ACTIVE` встановлюється, коли користувач приймає квест.
- `COMPLETED` встановлюється системою лише після досягнення цільового показника.
- Після `COMPLETED` квест не може бути скасований або повторно активований.
- Новий квест може бути запропонований після завершення попереднього.

## Quest Types

| Type | Description | Completion Condition |
|---|---|---|
| `STEP_TARGET` | Квест на проходження заданої кількості кроків. | Поточна кількість кроків >= цілі. |
| `ROUTE` | Квест на проходження реальної відстані між двома точками. | Накопичена відстань >= довжини маршруту. |
| `CUSTOM` | Налаштовуваний користувачем квест. | Виконується задана користувачем ціль, що пройшла валідацію. |

Для `ROUTE` квесту:
- `startPoint` і `endPoint` визначаються користувачем;
- `routeDistance` отримується через зовнішній картографічний сервіс;
- домен не залежить від конкретної реалізації Google Maps API;
- якщо зовнішній сервіс не повернув коректну відстань, квест не може бути підтверджений як готовий до виконання.

## Domain Policies

| Domain Policy | Description |
|---|---|
| `AcceptQuestDPolicy` | Перевіряє, чи доступний квест для прийняття користувачем. |
| `CompleteQuestDPolicy` | Перевіряє досягнення цільового показника та дозволяє завершення активного квесту. |
| `CreateRouteQuestDPolicy` | Перевіряє наявність двох валідних точок і додатної довжини маршруту. |
| `UpdateQuestProgressDPolicy` | Не дозволяє від'ємний прогрес і некоректне збільшення показників активності. |
| `UnlockAchievementDPolicy` | Перевіряє умову досягнення та гарантує одноразове отримання конкретного досягнення. |
| `ApplyActivityDPolicy` | Перевіряє, що запис активності має валідні невід'ємні значення та може бути застосований до прогресу. |

## Key Flow: Activity → Quest → Reward

1. Пристрій або Google Fit передає дані про активність.
2. `Application` приймає дані та передає їх домену.
3. `ActivityRecord` проходить перевірку `ApplyActivityDPolicy`.
4. Валідна активність зберігається.
5. Активний квест отримує новий прогрес.
6. Якщо ціль досягнута, `CompleteQuestDPolicy` дозволяє завершити квест.
7. Система створює `QuestCompletedDE`.
8. `EvaluateAchievementsService` перевіряє умови досягнень.
9. За виконання умови створюється `AchievementUnlockedDE`.
10. Оновлюється рівень користувача, якщо досягнуто відповідної межі.
11. Application/Infrastructure синхронізує дані з Firebase для авторизованого користувача.
12. Наступний доступний квест може бути запропонований користувачу.

**Boundary:** Domain відповідає за правила, інваріанти та зміни стану. Application відповідає за оркестрацію. Infrastructure відповідає за сенсори, Google Fit, Google Maps, Firebase та push-сервіси.

## Infrastructure

### Persistence

Локальне сховище повинно містити щонайменше:
- користувача та його прогрес;
- квести та їхній статус;
- прогрес активних квестів;
- історію активності;
- досягнення;
- локальні налаштування.

Для авторизованого користувача локальні дані синхронізуються з Firebase. Локальне збереження має залишатися працездатним без постійного підключення до інтернету.

### External Integrations

- Google Fit — джерело фізичної активності на Android.
- Google Maps API — побудова та визначення довжини маршрутів.
- Firebase — віддалене збереження та синхронізація.
- Push-notification service — нагадування про активність.
- Google Analytics / Firebase Analytics — технічна та продуктова статистика використання.

Зовнішні API не викликаються безпосередньо з Domain.

## Localization

Поточний домен не зберігає текст інтерфейсу як бізнес-логіку. Основна локалізація:
- українська — основна;
- англійська — додаткова;
- адміністративна панель — англійською.

Назви та описи квестів, досягнень і системних повідомлень мають бути локалізованими на рівні Presentation/Application, а не зашитими в Domain.
