> Ця політика визначає обов'язкові вимоги до коду та архітектури `Stroll` — мобільного Android-застосунку для мотивації фізичної активності через кроки, маршрути, квести, досягнення та статистику. Ключові вимоги: строго типізоване ООП, SOLID, чистий код, розділення шарів, ізоляція бізнес-логіки від Android Framework та зовнішніх сервісів, а також тестування бізнес-правил.

> Проєкт на початковому етапі підтримує Android 8.0+ та портретну орієнтацію. Підтримка iOS, Apple Health та смарт-годинників розглядається як майбутнє розширення і не повинна проникати в поточну Android-реалізацію через жорсткі залежності Domain.

## Правила зміни політики

- **Жодних змін мимохідь** — політика не змінюється як побічний ефект іншої задачі.
- **Обов'язковий апрув** — зміни погоджуються з власником проєкту.
- **Окремий комміт + інкремент версії** — зміни політики виконуються окремим коммітом з префіксом `[POLICY]` та оновленням версії.
- Зміни політики не повинні використовуватися для виправдання порушення вже встановлених архітектурних меж.

## Скоуп

Політика поширюється на:
- Kotlin-код мобільного застосунку;
- Domain, Application, Infrastructure та Presentation;
- локальне сховище;
- інтеграції Google Fit, Google Maps API, Firebase та push-notification service;
- тести;
- документацію, що описує поточну архітектуру та бізнес-логіку.

Політика не визначає внутрішню реалізацію сторонніх сервісів.

## Технології

- **Kotlin** — основна мова розробки.
- **Android Studio** — середовище розробки.
- **Android 8.0+ (API 26+)** — мінімальна цільова версія.
- **Google Fit API** — отримання даних фізичної активності на Android.
- **Google Maps API** — карти, точки та маршрути.
- **Firebase** — віддалене збереження та синхронізація даних.
- **Push-notification service** — нагадування та системні повідомлення.
- **Google Analytics / Firebase Analytics** — продуктова статистика.
- **Room або еквівалентний локальний persistence layer** — локальне збереження.
- **JUnit** та інструменти Android/Kotlin testing — тестування.
- **Git** — контроль версій.

Конкретна бібліотека може бути замінена еквівалентною лише після перевірки сумісності з цією політикою.

## Фундаментальні принципи

- **Розділення шарів.** Presentation, Application, Domain та Infrastructure не змішуються.
- **DDD для бізнес-логіки.** Квести, прогрес, активність, досягнення та рівні моделюються як доменні поняття.
- **Чужа логіка поза проектом.** Stroll не дублює бізнес-правила Google Fit, Google Maps, Firebase або Android.
- **Інверсія залежностей.** Domain не залежить від Android Framework, Google Fit, Google Maps або Firebase SDK.
- **Строго типізоване ООП, SOLID, чистий код.**
- **Offline-first для локальної активності.** Основні дані активності не повинні втрачатися через тимчасову відсутність інтернету.
- **Безпека даних.** Облікові дані, токени та інші секрети не зберігаються у відкритому вигляді.
- **Мінімізація дозволів.** Застосунок запитує лише ті дозволи, які потрібні для заявленої функціональності.
- **Фреймворк не проникає в Domain.** Android lifecycle, Context, Activity, Fragment, ViewModel та SDK-типи не використовуються у чистих доменних сутностях.
- **Непорушність політики.** Виявлені розбіжності виправляються, а не обходяться локальними винятками без документованого рішення.

## Архітектура та структура

Рекомендована структура:

```text
app/
└── src/
    ├── main/
    │   ├── java/.../
    │   │   ├── presentation/
    │   │   ├── application/
    │   │   ├── domain/
    │   │   └── infrastructure/
    │   └── res/
    └── test/
```

Логічні шари:

```text
Presentation → Application → Domain
                         ↘ Infrastructure
Domain ← contracts ← Infrastructure
```

### Domain

Domain містить:
- `Entity/`
- `ValueObject/`
- `Enum/`
- `Exception/`
- `OutsourceContract/`
- `Service/`
- `Policy/`
- `Event/`

Domain не повинен імпортувати:
- `android.*`;
- Google Fit SDK;
- Google Maps SDK;
- Firebase SDK;
- класи бази даних;
- UI-класи;
- HTTP-клієнти.

### Application

Application містить:
- `UseCase/`;
- `Command/`;
- `Query/`;
- `Dto/`;
- `Exception/`.

Application оркеструє сценарії, але не містить бізнес-правил. Наприклад, `AcceptQuestUC` може отримати квест, викликати доменну політику та зберегти результат, але саме правило допустимості прийняття квесту живе в Domain.

### Infrastructure

Infrastructure містить:
- `Persistence/`;
- `External/GoogleFit/`;
- `External/GoogleMaps/`;
- `External/Firebase/`;
- `Notifications/`;
- `Analytics/`;
- `Exception/`.

Infrastructure реалізує контракти, оголошені Domain.

### Presentation

Presentation містить:
- Activity / Fragment / Compose UI;
- ViewModel;
- navigation;
- permission handling;
- відображення стану та помилок;
- локалізовані ресурси.

Presentation не містить правил завершення квесту, розрахунку винагород або інших доменних рішень.

## Політика доменних івентів

Кожен Domain Event повинен містити:
- унікальний ідентифікатор;
- ідентифікатор сутності-джерела;
- час створення;
- тип події;
- версію схеми;
- типізований payload.

Для Stroll використовуються, зокрема:
- `ActivityRecordedDE`;
- `QuestAcceptedDE`;
- `QuestProgressUpdatedDE`;
- `QuestCompletedDE`;
- `AchievementUnlockedDE`;
- `UserLevelChangedDE`.

Події не повинні містити:
- access token;
- refresh token;
- персональні секрети;
- сирі дані сенсорів;
- повні відповіді зовнішніх API.

Домен створює подію у внутрішній черзі. Application зберігає зміну стану, після чого Infrastructure може передати подію відповідним обробникам.

## Політика неймінгу

- Класи, інтерфейси, enum — `PascalCase`.
- Методи, змінні, параметри — `camelCase`.
- Константи — `UPPER_SNAKE_CASE`.
- Пакети — `lowercase`.
- Файл Kotlin відповідає основному типу або логічній групі типів.
- Інтерфейси — префікс `I` не є обов'язковим для Kotlin; перевага надається іменам на кшталт `QuestRepository`, `RouteProvider`.
- Value Object — суфікс `VO`, якщо це відповідає узгодженій структурі Domain.
- Domain Service — суфікс `Service`.
- Domain Policy — суфікс `DPolicy`.
- Domain Event — суфікс `DE`.
- Use Case — суфікс `UC`.
- Application Command — суфікс `AC`.
- Application Query — суфікс `AQ`.
- DTO — суфікс `DTO`.
- Виняток — суфікс `Exception`.

Приклади:
- `Quest`;
- `QuestProgressVO`;
- `CreateRouteQuestDPolicy`;
- `CalculateQuestProgressService`;
- `QuestCompletedDE`;
- `AcceptQuestUC`;
- `CreateRouteQuestAC`;
- `GetActiveQuestAQ`.

## Політика документації коду

Для кожного публічного класу та методу, де це потрібно для розуміння контракту, повинна бути документація, яка описує:
- призначення;
- обмеження;
- параметри;
- результат;
- винятки;
- бізнес-інваріанти для Entity та Value Object.

Документація не повинна просто переказувати код.

Для доменних Entity обов'язково документуються ключові інваріанти.

## Політика винятків

Усі помилки Domain та Application повинні мати типізовані внутрішні винятки.

Приклади:
- `QuestNotFoundException`;
- `InvalidQuestTransitionException`;
- `InvalidRouteException`;
- `InvalidActivityRecordException`;
- `AchievementAlreadyUnlockedException`;
- `ExternalServiceException`.

Сирі винятки Google Fit, Google Maps, Firebase або мережевих бібліотек не повинні виходити за межі Infrastructure.

Infrastructure перетворює зовнішню помилку на внутрішній типізований виняток із безпечним повідомленням.

## NULL-less політика

У Domain рекомендується мінімізувати використання `null` як логічного стану.

Перевага надається:
- nullable лише там, де відсутність є природною частиною даних;
- sealed interface;
- спеціальним Value Object;
- порожнім колекціям замість `null`;
- enum для станів.

Наприклад, відсутність маршруту в `DRAFT` квесті повинна бути частиною валідного стану створення, але після переходу в `AVAILABLE` маршрутний квест повинен мати обидві точки та розраховану відстань.

## Політика роботи із зовнішніми сервісами

### Google Fit

- Google Fit використовується лише через `StepActivityProvider`.
- Domain не знає про Google Fit API.
- Отримані дані нормалізуються до `ActivityRecord`.
- Повторна синхронізація не повинна дублювати активність.

### Google Maps API

- Google Maps використовується лише через `RouteProvider`.
- Domain працює з `GeoPointVO` та `DistanceVO`.
- API key не зберігається у вихідному коді.
- Помилки мережі та API перетворюються на внутрішні Infrastructure/Application помилки.
- Квест не переводиться у готовий стан без валідної довжини маршруту.

### Firebase

- Firebase використовується через Infrastructure.
- Domain не залежить від Firebase SDK.
- Синхронізація не повинна знищувати локальні дані через тимчасову відсутність мережі.
- Конфлікти синхронізації повинні мати визначене правило розв'язання до реалізації функції multi-device sync.

### Push notifications

- Domain визначає подію або факт, який може вимагати нагадування.
- Infrastructure відповідає за фактичну доставку push-повідомлення.
- Notification token є технічними даними Infrastructure і не передається в Domain.

## Політика зберігання та синхронізації даних

- Активність користувача зберігається локально незалежно від наявності облікового запису.
- Для авторизованого користувача дані синхронізуються з Firebase.
- Локальна база є джерелом доступних offline-даних на пристрої.
- Записи активності повинні мати стабільний ідентифікатор для дедуплікації.
- Операції синхронізації повинні бути ідемпотентними.
- Видалення або перезапис даних не виконується лише через тимчасову помилку мережі.
- Стан квесту та отримані досягнення не повинні втрачатися при перезапуску застосунку.
- Дані, необхідні для роботи без інтернету, не повинні залежати від постійного доступу до зовнішнього API.

## Політика дозволів та приватності

- Доступ до фізичної активності та геолокації запитується лише за необхідності.
- Користувач повинен отримувати зрозуміле пояснення призначення дозволу.
- Дані геолокації використовуються для функцій, пов'язаних із маршрутами.
- Необхідно мінімізувати збирання даних, які не потрібні для роботи функцій.
- Секрети API та токени не комітяться до Git.
- Конфігураційні секрети передаються через безпечний механізм конфігурації середовища/збірки.
- Аналітичні події не повинні містити чутливі персональні дані.

## Політика тестування

### Інструменти

Основа — Kotlin/JUnit та Android testing tools.

Зовнішні залежності замінюються fake/mock реалізаціями. Domain-тести не виконують реальних мережевих викликів.

### Пріоритет

Обов'язково тестуються:
- інваріанти Entity;
- Value Object;
- переходи статусів квесту;
- політики;
- розрахунок прогресу;
- завершення квесту;
- нарахування досягнень;
- зміна рівня;
- дедуплікація активності;
- offline-сценарії Application;
- помилки зовнішніх інтеграцій.

Позитивні сценарії повинні доповнюватися негативними:
- нульова або від'ємна ціль;
- від'ємні кроки;
- некоректні координати;
- повторне завершення квесту;
- повторне отримання досягнення;
- дубль активності;
- недоступний маршрут;
- відсутність мережі.

### Розподіл тестів

- **Domain:** unit tests без Android.
- **Application:** unit tests Use Case з mock/fake залежностями.
- **Infrastructure:** unit та integration tests із замоканими зовнішніми сервісами.
- **Presentation:** UI/instrumentation tests для критичних користувацьких сценаріїв.

Реальні Google Fit, Google Maps та Firebase виклики не використовуються у звичайних unit tests.

## Git Workflow

### Гілки

| Гілка | Призначення |
|---|---|
| `main` | Стабільна версія проєкту |
| `develop` | Поточна інтеграційна розробка |
| `feature/*` | Окрема функціональність |

### Повідомлення коммітів

```text
[тип] короткий підсумок
```

Рекомендовані типи:
- `FEAT` — нова функціональність;
- `FIX` — виправлення;
- `REFACTOR` — зміна структури без зміни поведінки;
- `TEST` — тести;
- `DOCS` — документація;
- `POLICY` — зміна політики;
- `BUILD` — конфігурація збірки.

### CI-перевірки

Перед merge повинні проходити:
- збірка проєкту;
- Kotlin lint/static analysis;
- unit tests;
- перевірка залежностей;
- перевірка відсутності секретів у репозиторії.

## Локалізація

Підтримувані мови:
- українська — основна;
- англійська — додаткова.

Всі UI-рядки зберігаються у ресурсах локалізації, а не в Kotlin-коді.

Доменні сутності не повинні містити жорстко закодованих UI-текстів.

Адміністративна панель використовує англійську мову.
